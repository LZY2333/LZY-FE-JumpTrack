# CIPS 报文动态表单建设方案

## 建设背景、目标与范围

CIPS 报文数量多、字段层级深，不同报文之间又存在大量重复结构。

如果每种报文分别开发 React 表单，会产生大量重复代码，后续报文升级时维护成本也会持续增加。

当前阶段主要解决前端问题：

- 报文录入和编辑；
- 报文详情可视化；
- 字段格式校验；
- 字段联动；
- 报文版本适配；
- 表单数据与业务数据转换。

以下能力不属于前端表单引擎范围：

- 数字签名和验签；
- 证书及密钥管理；
- CIPS 通信；
- 报文发送和接收；
- 最终 XML 合规校验；
- 清算业务处理。

## CIPS 报文分析与前端建设挑战

CIPS 完整规范包含数十种报文。公开的资金清算规范中，包括49种人民币报文和35种外币报文。

单个复杂报文可能包含上百个结构节点。例如客户汇款报文约有120个编号节点，但其中包含大量对象、容器和可重复节点，实际用户输入字段通常为25～50个。

前端主要面临以下问题：

- 字段数量多；
- XML结构层级深；
- 存在大量可选对象；
- 地址、附件、监管信息等结构可以重复；
- 部分字段条件显示、条件必填；
- 部分字段至少填写一个；
- 部分字段互斥；
- 同一报文存在多个版本；
- 大量报文只有查看需求，没有编辑需求。

因此不建议为每种报文单独开发静态页面，建议采用 __Schema 驱动的动态表单__

建议首期只支持10～15种高频报文，其他报文先通过通用树形视图和 XML 视图展示。

## Schema 驱动的动态表单

Schema 驱动是指使用配置描述字段、页面和规则，由统一的表单引擎动态生成页面。

```text
Schema 配置
    ↓
动态表单渲染器
    ↓
React 表单
    ↓
Ant Design 组件
```

Schema 通常包含三类信息：

- Data Schema：字段类型、长度、层级、必填和数组数量；
- UI Schema：组件类型、页面分组、排列顺序和只读状态；
- Rule Schema：显示、隐藏、条件必填、禁用、互斥和跨字段校验。

简单示例：

```ts
const schema = {
  fields: [
    {
      name: "partyType",
      label: "主体类型",
      component: "select",
      options: ["PERSON", "ORGANIZATION"],
    },
    {
      name: "privateId",
      label: "个人证件号码",
      component: "input",
      maxLength: 35,
      visibleWhen: {
        field: "partyType",
        equals: "PERSON",
      },
      requiredWhen: {
        field: "partyType",
        equals: "PERSON",
      },
    },
  ],
};
```

新增报文时，主要增加 Schema 配置，不需要重新开发完整的 React 页面。

## Formily 选型与能力评估

Formily 是一套开源动态表单解决方案，提供表单状态管理、Schema 渲染、字段联动和 Ant Design 组件适配。

主要模块包括：

- `@formily/core`：表单状态和联动引擎；
- `@formily/react`：React 渲染能力；
- `@formily/antd`：Ant Design 组件；
- Designable：可选的拖拽表单设计器。

Formily适合CIPS场景的主要原因：

- 支持 JSON Schema；
- 支持嵌套对象和动态数组；
- 支持字段级响应式更新；
- 支持条件显示、禁用和只读；
- 支持自定义校验；
- 支持自定义组件；
- 可以直接使用 Ant Design。

__Formily 能解决 表单动态渲染、联动校验 以及 字段太多导致的性能问题__

__但不能直接解决 CIPS XML 映射、报文版本和业务规则治理问题__

因而需要 同步建设 __CIPS-adapter__ + __CIPS-schema__

## CIPS Schema 模型设计

CIPS Schema 应描述 CIPS 业务含义，不直接依赖 Formily 和 Ant Design。

简单字段模型示例：

```ts
interface CipsFieldSchema {
  name: string;
  path: string;
  xmlPath: string;

  label: string;
  dataType: string;
  component: "input" | "select" | "amount" | "date" | "group" | "list";

  required?: boolean;
  readonly?: boolean;
  maxLength?: number;

  minOccurs?: number;
  maxOccurs?: number | "unbounded";

  visibleWhen?: Condition;
  requiredWhen?: Condition;
  disabledWhen?: Condition;

  atLeastOneOf?: string[];
  mutuallyExclusive?: string[];

  validators?: ValidatorConfig[];
}
```

字段配置示例：

```ts
const debtorIdField: CipsFieldSchema = {
  name: "privateId",
  path: "debtor.identification.privateId",
  xmlPath: "Dbtr/Id/PrvtId/Othr/Id",

  label: "付款人证件号码",
  dataType: "Max35Text",
  component: "input",
  maxLength: 35,

  visibleWhen: {
    field: "debtor.type",
    operator: "equals",
    value: "PERSON",
  },

  requiredWhen: {
    field: "debtor.type",
    operator: "equals",
    value: "PERSON",
  },
};
```

首期建议支持以下规则：

- `visibleWhen`：条件显示；
- `requiredWhen`：条件必填；
- `disabledWhen`：条件禁用；
- `atLeastOneOf`：多个字段至少填写一个；
- `mutuallyExclusive`：多个字段不能同时填写；
- `valueFrom`：从其他字段自动取值；
- `clearWhenHidden`：隐藏时清空字段；
- `validators`：长度、格式和自定义校验。

复杂业务逻辑允许使用自定义规则函数处理，不要求所有规则都通过简单 JSON 表达。

## CIPS Schema Adapter: 领域隔离设计

Formily Schema 属于应用层，描述页面如何实现

CIPS Schema 属于领域层，描述业务标准

CIPS Adapter 将 CIPS Schema 转换为 Formily Schema

推荐增加 Adapter：

```text
CIPS Schema
    ↓
CIPS Schema Adapter
    ↓
Formily Schema
    ↓
Formily SchemaField
    ↓
Ant Design 页面
```

Adapter 主要负责：

- CIPS字段类型转换为Formily字段类型；
- CIPS组件名称转换为AntD组件；
- CIPS校验规则转换为`x-validator`；
- CIPS联动规则转换为`x-reactions`；
- CIPS页面分组转换为Formily布局组件。

简单示例：

```ts
const componentMap = {
  input: "Input",
  select: "Select",
  amount: "NumberPicker",
  date: "DatePicker",
};

function adaptField(field: CipsFieldSchema) {
  return {
    type: mapDataType(field.dataType),
    title: field.label,
    maxLength: field.maxLength,

    "x-decorator": "FormItem",
    "x-component": componentMap[field.component],
    "x-validator": mapValidators(field),
    "x-reactions": mapReactions(field),
  };
}
```

完整转换入口：

```ts
function adaptCipsSchemaToFormily(
  schema: CipsMessageSchema,
): ISchema {
  return {
    type: "object",
    properties: Object.fromEntries(
      schema.fields.map((field) => [
        field.name,
        adaptField(field),
      ]),
    ),
  };
}
```

Adapter 推荐属于前端，因为它依赖 Formily 和 Ant Design。

后端只保存 CIPS Schema，前端获取后进行转换：

```tsx
const cipsSchema = await getCipsSchema(
  "cips.111.001.02",
);

const formilySchema =
  adaptCipsSchemaToFormily(cipsSchema);

return (
  <SchemaField schema={formilySchema} />
);
```

表单数据转换为正式 CIPS XML、XSD 校验和签名仍建议由后端完成。前端可以提供 XML 预览，但不作为最终发送依据。

## 项目前期实施方案

主要方案：

- CIPS Schema 使用 JSON 文件维护, 甚至可以脚本生成；
- Schema 文件进入 Git；
- Schema 变更通过代码评审；
- 每个 Schema 明确报文编号和版本；
- 建设统一的动态表单渲染器；
- 建设 CIPS Schema Adapter；
- 建设通用字段组件和布局组件；
- 建设表单数据与业务 JSON 的转换能力；
- 后端负责最终 XML 生成和校验。

推荐先选择三种代表性报文：

- 简单报文：状态查询；
- 中型报文：撤销或查复；
- 复杂报文：客户汇款 `cips.111`。

验证内容包括：

- 嵌套字段；
- 动态数组；
- 条件显示；
- 条件必填；
- 至少填写一个；
- 互斥字段；
- 隐藏字段清理；
- 只读模式；
- 表单数据回显；
- 报文版本切换。

首期目标是验证动态表单架构，不追求一次性覆盖全部 CIPS 报文。

## Schema 版本治理与质量保障

Schema 应通过“报文编号＋版本号”唯一标识：

```text
cips.111.001.02@2023
cips.111.001.03@2026
```

版本治理至少需要包括：

- Schema 版本记录；
- 变更内容说明；
- Git 评审；
- 新旧字段差异比较；
- 历史版本保留；
- 配置回滚；
- 报文实例绑定 Schema 版本。

测试重点包括：

- Schema 本身的结构校验；
- 字段必填和长度校验；
- 联动规则单元测试；
- 互斥和至少填写一个测试；
- 动态数组测试；
- 表单数据回显测试；
- 旧版本报文只读展示；
- 业务 JSON 与 XML 双向转换测试。

生产环境不建议允许业务人员直接修改并立即生效。Schema 应经过编辑、测试、审核和发布流程。

## 后续演进：统一报文表单引擎与配置平台

CIPS稳定运行之后，可以将动态表单能力从 CIPS 业务系统中拆分出来，形成 __统一报文表单渲染引擎__。

统一表单引擎主要提供：

- Schema解析；
- 动态表单渲染；
- 只读报文展示；
- 规则执行；
- 字段校验；
- 动态数组；
- 自定义组件注册；
- 数据转换；
- 版本兼容。

可以封装成统一组件：

```tsx
<MessageForm
  messageCode="cips.111.001.02"
  version="2023"
  mode="edit"
  value={messageData}
  onChange={setMessageData}
/>
```

在统一引擎稳定后，再建设 __统一报文表单接入配置平台__

配置平台可以提供：

- 报文配置页面；
- 字段配置页面；
- 页面布局配置；
- 联动规则配置；
- 字典配置；
- 实时表单预览；
- Schema差异比较；
- 测试数据管理；
- 发布和回滚；
- 权限和审核；
- 操作审计。

最终形成统一的报文规则中心：

```text
报文配置平台
    ↓
统一 CIPS Schema
    ↓
统一报文表单引擎
    ↓
CIPS、SWIFT及其他金融报文页面
```

平台建设应分阶段进行：先形成稳定的运行引擎和规则模型，再建设可视化配置页面，避免在规则模型尚未稳定时过早投入低代码平台建设。
