# 数据库设计

## 1. 数据表分类

在进行数据库设计前，我们首先应该对数据表的分类有一个总体性的认识，这个认识可以来源于各项规范，也可以是基于对本系统群的整体性了解所做的归纳，明确数据表的分类可以更好地在数据表设计过程中明确表的边界，确定各个数据的归属，避免出现表或字段定位模糊的问题。

### 1.1. 数据表的类别

从使用场景上可以将数据表划分为**业务作用表**、**技术作用表**及**配置表**三大类，随后根据表在系统中的作用和定位可以进一步细分如下：

| 表作用 | 表类型 | 定义 |
| --- | --- | --- |
| 配置表 | 参数表 | 系统运行过程中需要使用和依赖的参数数据。 |
| 配置表 | 数据字典表 | 各数据表中特定字段的枚举定义说明，主要用于辅助理解和查询，系统不依赖此表。 |
| 业务作用表 | 实体表 | 记录对象实体及其属性信息。 |
| 业务作用表 | 外部数据表 | 由系统外部提供的数据，通常是市场数据或请求数据。 |
| 业务作用表 | 交易表 | 标示交易演进方向和演进过程的表，记录交易的一系列类型、状态等基本信息。 |
| 业务作用表 | 日志表 | 跟踪用户或客户的操作日志，包括登录、数据修改、交易审批等操作。 |
| 技术作用表 | 操作表 | 用于记录各数据表的操作过程表，通常会记录每次数据变动的所有版本。 |
| 技术作用表 | 历史表 | 来自交易表的历史备份，与交易表不会有重复数据。 |
| 技术作用表 | 备份表 | 用于临时备份数据的表。 |

### 1.2. 业务作用表

业务作用表是一系列具有业务用途，用户或客户可直接查询和管理的数据表，初步可以分为实体表、外部数据表、交易表及日志表。

#### 1.2.1. 实体表

任何可以独立存在并被唯一标识的对象即是实体，因此实体表可以不依赖其他表而存在。同时根据不同业务的要求，实体间也可能存在一定的关联关系，这些关联关系不对表的使用产生强约束，在开展相关业务时原则上应该是可以独立运作的，因此根据业务需要和系统规划，也可能将部分存在关联关系的实体及表分散的不同的业务系统处理。

另外根据业务需要，单一实体可能会产生数百乃至上千种属性，根据不同业务类型这些数据的应用场景也不尽相同，因此实体表还应根据不同业务拆分为基本信息表、类型信息表、实体属性表三项。

| 表类型 | 表细类 | 定义 |
| --- | --- | --- |
| 实体表 | 基本信息表 | 存放实体的唯一编号及各项不会产生变化的基本信息及类型值，用于唯一标识实体本身以及实体的基本属性。 |
| 实体表 | 类型信息表 | 依赖基本信息表存在，用于存储不同类型下的实体独特信息，通常与基本信息表的数据一一对应。 |
| 实体表 | 实体属性表 | 依赖基本信息表或类型信息表存在，是关于实体信息的属性补充信息，通常与依赖表的数据呈多对一关联。 |

实体表间的关联关系以及不同实体表细类的依赖关系整体形成一个树状的实体关系结构，示例如下：

```text(实体表树状图示意)
基本信息表A ─ ─ ─ 关联 ─ ─ ─▶ 基本信息表B
│
├── 类型信息表A1
│   └── 实体属性表A1-1
├── 类型信息表A2
├── 类型信息表A3
│   ├── 实体属性表A3-1
│   └── 实体属性表A3-2
└── 实体属性表A4
```

#### 1.2.2. 外部数据表

由系统外部进入系统内的数据则是外部数据，原则上外部数据表的设计完全依赖外部数据结构，系统在收到数据的第一时间记录外部原始数据，随后进行业务方面的使用，主要是查询展示、数据加工、流程发起等，外部数据的留存时间通常随业务需要而变化，当数据的业务使用完成后即可归档相关数据。

根据外部数据的使用方式通常还可将外部数据表分为市场数据表及系统外请求表两类，市场数据表通常是储存结构化的数据信息，常用于查询展示及为关联业务提供市场数据进行加工，如股价、汇率信息等；系统外请求表通常用于流程类系统中，用于第一时间记录外部原始数据，系统随后依据外部原始数据发起系统的业务流程。

| 表类型 | 表细类 | 定义 |
| --- | --- | --- |
| 外部数据表 | 市场信息表 | 储存结构化的市场数据信息，常用于查询展示及为关联业务提供市场数据进行加工，如股价、汇率信息等。 |
| 外部数据表 | 系统外请求表 | 常用于流程类系统中，用于第一时间记录外部原始数据，系统随后依据外部原始数据发起系统的业务流程。 |

#### 1.2.3. 交易表

交易表主要存放业务过程信息，其特征是交易表的数据存在一个“终点”，通常我们以交易表状态字段中的终态来表示这个“终点”，相对应的交易表也存在起始状态和中间状态。

在交易的业务处理过程中，通常会在不同的节点与外围系统产生交互，或需要在系统内进行复杂或标准化的其他业务处理，由于系统外的处理和标准化模块存在自己的状态流转和时序，因此在此类场景下通常会通过新的表记录此类交互的基本信息及状态流转，该新表与系统最初产生的交易表存在依赖关系，因此我们可以将交易表分为交易主表及交易子表。

同时在各种不同业务场景下，通常一笔交易会因为各项业务属性的不同产生众多需要特殊处理的分支，也需要根据业务属性的不同记录众多不同的业务附加信息，因此还存在交易的附加信息表，附加信息表依赖于交易主表或子表存在。

| 表类型 | 表细类 | 定义 |
| --- | --- | --- |
| 交易表 | 交易主表 | 标示交易演进方向和演进过程的表，记录交易的一系列类型、状态等基本信息。 |
| 交易表 | 交易子表 | 在交易主流程中衍生的额外流程记录表，如系统内的任务流程、复杂业务处理流程或标准化业务处理模块、与外部系统交互流程信息的记录等。 |
| 交易表 | 附加信息表 | 在交易过程中产生的附加信息，本身无状态，依赖主表或子表存在。 |

交易的完整信息由交易主表、交易子表、附加信息表共同构成，其依赖关系通过业务流程产生，表关系整体形成一个线性的实体关系结构，示例如下：

```text(交易表线性图示)
交易主线：
开始 ─▶ 交易主表 ─▶ 节点1 ─▶ 节点2 ─▶ 节点3 ─▶ 节点4 ─▶ 节点5 ─▶ 结束

交易主表 ─┬─▶ 交易主表附加信息表1
           ├─▶ 交易主表附加信息表2
           └─▶ 交易主表附加信息表3

节点1 ───────────────▶ 交易子表A
节点1、节点2、节点3 ─▶ 交易子表B ─▶ 交易子表B附加信息表1
节点3 ───────────────▶ 交易子表C ─▶ 交易子表C附加信息表1
节点4 ───────────────▶ 交易子表D ─▶ 交易子表D附加信息表1
节点5 ───────────────▶ 交易子表E ─┬─▶ 交易子表E附加信息表1
                                  └─▶ 交易子表E附加信息表2
```

#### 1.2.4. 日志表

日志表通常用于跟踪用户或客户的操作日志，包括登录、数据修改、交易审批等操作。日志表常依赖于交易表存在，交易表存储操作的结果信息，日志表则存储操作的过程信息。

### 1.3. 技术作用表

技术作用表是因技术方面的需要，基于业务作用表而产生的表，其数据结构与源表结构基本一致，根据不同的技术需要，可以将其分为操作表、历史表、备份表，其定义较为简单，不再赘述，但需要强调，技术作用表并非不参与业务处理，如操作表一般是经办人员处理业务的过程数据，是审批人员需要查看的信息；历史表则会有业务查询的需要。

### 1.4. 配置表

用于存储系统、程序或业务流程中可变参数或规则的表格形式的数据结构，根据业务是否依赖使用还可分为参数表和数据字典表。

#### 1.4.1. 参数表

系统运行过程中需要使用和依赖的参数数据，通常以键值对、字段组合或规则集合的形式存在，用于控制系统功能行为、调整逻辑流程、管理参数设置等。根据用户是否允许修改相关参数还可分为业务参数表和系统参数表。

| 表类型 | 表细类 | 定义 |
| --- | --- | --- |
| 参数表 | 业务参数表 | 业务人员或客户可控制或修改的参数表，通常按照业务场景细分不同的表存放。 |
| 参数表 | 系统参数表 | 业务人员或客户不可控制的参数表，如各开关配置、阈值、路由规则、系统配置数据等。 |

#### 1.4.2. 数据字典表

各数据表中特定字段的枚举定义说明，主要用于辅助理解和查询，系统不依赖此表。

| 表类型 | 表细类 | 定义 |
| --- | --- | --- |
| 数据字典表 | 数据字典类型表 | 记录数据字典类型信息。 |
| 数据字典表 | 数据字典码值表 | 记录数据字典码值。 |

## 2. 业务作用表设计

### 2.1. 实体表

实体表的设计总体而言是面对对象的，进行实体表设计时并不一定需要将所有的实体表都按照基本信息表、类型信息表、实体属性表进行拆分，部分属性较少的实体可能仅一张表即可完成全部设计，但我们也可以将其归类为基本信息表的范畴以便分类管理。

当遇到实体属性较多（以 128 个字段为限）或存在较多可合并数据与实体信息呈多对一关系或考虑到实体表的扩展性等情况时，则需要为实体对象拆分出类型信息表及实体属性表，其余信息则作为基本信息表存在。

#### 2.1.1. 类型信息表

类型信息表通常是当实体在不同类型下需要存储不同数据时应当拆分出的表，在表关系上基本信息表与类型信息表是一对多关系，而在数据上则通常是一对一关系。因此类型信息表可以看作是实体属性的延伸，同一实体的不同类型信息表之间可能存在相同或相似的字段，这类字段无需提炼到基本信息表中，将其放在类型信息表中可以保持基本信息表的纯粹，当后续出现新的实体类型时也便于扩展。

类型信息表依赖基本信息表存在，因此类型信息表通常不需要单独的唯一流水号，应使用基本信息表的实体唯一编号作为类型信息表的主键。如果类型信息表有较为独立的业务使用场景或有与实体属性表关联，则可以生成单独的业务流水号作为业务使用或依赖关系的依据。

#### 2.1.2. 实体属性表

实体属性表依赖于基本信息表或类型信息表产生，其拆分依据通常是基于以下几类情况出发：

1. 高敏感或高保密数据单独保存管理，如密码信息。
2. 高频读/写数据独立管理，如额度信息。
3. 实体中可以分类管理的同质数据，通常与基本信息表或类型信息表数据是多对一关系，如地址信息。
4. 需要独立处置的一系列业务数据，如证件图像信息。

实体属性表通常处于依赖的底端，如非业务需要，不必生成单独的流水号，应使用基本信息表的实体唯一编号或类型信息表的业务流水号作为实体属性表的编号，并结合类型字段（在数据多对一场景下）作为实体属性表的联合主键。

#### 2.1.3. 基本信息表

完成类型信息表和实体属性表的拆分后，剩余的无法拆分或不需要拆分的实体属性即可归类为基本信息，同时基于上述依赖关系和表拆分原则的需要，实体的基本信息表还负责记录唯一流水号并作为主键存在，以及保存实体的各项主要类型信息。

#### 2.1.4. SWIFT 报文实体表设计示例

由于 SWIFT 报文根据业务场景的不同分类出了众多不同类型的报文，其报文格式存在较大差异，因此跨境报文实体可以根据报文类型拆分为调查类报文详情表、对账类报文详情表、支付类报文详情表等 SWIFT 报文的类型信息表，用于存放不同业务类型下的报文详情信息。

进一步地，在不同的类型信息表中可以根据实体属性表拆分的四项指引进一步拆解类型信息表，如调查类报文中还存在一类特殊的业务需要单独处理，因此还可分解出 GPI 属性表；支付类报文交易的各参与方（汇款人、汇款行、中转行、收款行、收款人等）则有着高度同质的信息，因此可以拆分出交易对象属性表，同时支付报文中也存在一类特殊的业务需要单独处理，因此可以分解出附加报文信息表。

同时每笔报文都需要单独进行反洗钱扫描的判定，此类业务需要集中处理，符合【高频读/写数据独立管理】的条件，因此将其独立成为反洗钱状态表。

总体的表设计示例图如下：

```text
│

├── 实体属性表A2
├── 实体属性表A3
│   ├── 实体属性表A3-1
│   └── 实体属性表A3-2
└── 实体属性表A4

SWIFT 报文实体表结构：

报文基本信息表 ─ ─ ─ 关联 ─ ─ ─▶ 子报文实体表
│
├── 调查报文详情表
│   └── GPI 属性表
├── 对账报文详情表
```

### 2.2. 交易表

交易表的设计总体而言是面对过程的，与实体表的设计在出发点上就有较大的区别，因此交易表的设计必须以交易主表为出发点进行设计，交易子表及附加信息表则是在交易的演进过程中随技术和业务需要逐步新增的表。

#### 2.2.1. 交易主表

交易主表最主要的职责即是用于管理交易的演进方向和演进过程，当交易产生时，主表需要存储该交易的唯一流水号，并可通过交易的类型字段判断交易需要经历的业务流程，通过交易的状态字段判断当前交易所处的阶段节点，因此交易的主表通常是有较高读写频率的。

由于交易主表的状态字段还承担着较为重要的交易流程控制职责，因此建议将与交易过程信息无关的其他基本信息均存入交易主表的附加信息表，以免其他附加信息的读写对交易主表读写的干扰。

#### 2.2.2. 交易子表

如同交易子表的定义，当交易流程发生需要与外围系统产生交互，或需要在系统内进行复杂或标准化的其他业务处理时，则需要通过交易子表独立地管理该交互或业务处理的过程。

与实体表的情况稍有不同，交易子表虽然依赖交易主表存在，但因其常需要与外围系统或外部系统交互，且这个交互可能是多次的，因此通常交易子表需要生成独立的唯一编号作为主键，并记录主交易流水号作为与主表关联的依据。

#### 2.2.3. 状态设计及分表依据

不论是交易主表或交易子表，交易的过程管理都依赖状态的流转进行，因此交易表中的状态设计尤为重要，状态设计的混乱也常是导致表设计过于复杂或系统对交易的控制不足的主要问题之一。

在进行状态设计前，应当先对交易过程中的几项重要行为进行如下定义：

1. 系统内的同步交互过程，交易数据是极易感知和查询的，可以称为强感知交互。
2. 系统外的同步交互过程，虽然结果数据会通过接口响应直接返回，但系统外的过程难以主动感知，因此可以称为弱感知交互。
3. 系统内的异步交互过程，交易无需实时关注交互结果，但有较为建议的主动感知交易过程的手段，可以称为可感知交互。
4. 系统外的异步交互过程，交易的执行过程需要依赖外围系统的主动通知或复杂的轮询机制进行检查，因此属于被动感知交互。

| 交互方式 | 系统外 | 系统内 |
| --- | --- | --- |
| 同步 | 弱感知 | 强感知 |
| 异步 | 被动感知 | 可感知 |

不同的交互感知在分表和状态设计上有着显著的差别，本文档暂不详述各交互感知在分表和状态设计方面的依据，仅提供结论。

1. 强感知交互通常不需要分表，状态设计上不必要为此类交互增加起始状态和成功状态，保留过程状态和失败状态即可。
2. 弱感知交互需要分表处理（交易子表），避免因系统外的状态变更影响交易主表的状态设计，主表中需要存在与交易子表的起始状态和终态对应的状态，无需关注交易子表的过程状态，因此主表中至少需要为每次弱感知交互增加开始、成功、失败三个状态。
3. 可感知交互需要分表处理（交易子表），通常情况下主表状态不需要与该类交易子表状态对应，两者互相独立，如业务方面需要将两表进行关联通常也仅是通过流水号关联查询处理，需要在状态上进行映射保存。
4. 被动感知交互需要分表处理（交易子表），如是通过接口交互的异步处理流程，则可以视为弱感知交互的延伸，使用当时拆分的交易子表处理，无需再次独立建表。由于被动感知交互总体较不可控，因此不建议将此类交互的状态设计在主表和子表的主要状态中，可以通过新的状态字段进行处理。被动感知交互通常需要交易主表和子表映射其失败状态，如无业务需要，其余业务状态不建议与交易主表及子表的状态进行匹配映射。

| 主表状态 | 起始状态 | 过程状态 | 失败状态 | 成功状态 |
| --- | --- | --- | --- | --- |
| 强感知 | 无 | 有 | 有 | 无 |
| 弱感知 | 有 | 无 | 有 | 有 |
| 可感知 | 无 | 无 | 无 | 无 |
| 被动感知 | 无 | 无 | 有 | 无 |

我们可以将交易的起始状态、过程状态、失败状态、成功状态定义为交易的四项基本状态，当交易仅存在一项强感知交互时，仅用这四项基本状态即可完成状态设计。在此基础上，如交易的过程中存在各类不同的交互，即可根据上述定义进行基本的状态设计，示例如下：

```text
开始
  │
  ▼
起始状态
  │
  ▼
处理中状态 ────────────────▶ 中间过程
  │                          │
```

#### 2.2.4. 附加信息表

附加信息表的定义与实体属性表类似，相关拆分依据、设计原则均可参考实体属性表进行判断。

但需强调附加信息表是依赖交易主表和子表存在，因此附加信息表的交易数据是临时性的，当交易结束后，附加信息表的数据也就不再有效，同时也不接受变更，这是其与实体属性表最大的差异。

## 附录一 数据表分类完整说明

| 表作用 | 表类型 | 细类 | 备注 |
| --- | --- | --- | --- |
| 配置表 | 参数表 | 业务参数表 | 业务人员或客户可控制或修改的参数表，通常按照业务场景细分不同的表存放。 |
| 配置表 | 参数表 | 系统参数表 | 业务人员或客户不可控制的参数表，如各开关配置、阈值、路由规则、系统配置数据等。 |
| 配置表 | 数据字典表 | 数据字典类型表 | 记录数据字典类型信息，仅作为技术参考，不作为系统依赖表使用。 |
| 配置表 | 数据字典表 | 数据字典码值表 | 记录数据字典码值，仅作为技术参考，不作为系统依赖表使用。 |
| 业务作用表 | 实体表 | 基本信息表 | 存放实体的唯一编号及各项不会产生变化的基本信息及类型值，用于唯一标识实体本身以及实体的基本属性。 |
| 业务作用表 | 实体表 | 类型信息表 | 依赖基本信息表存在，用于存储不同类型下的实体独特信息，通常与基本信息表的数据一一对应。 |
| 业务作用表 | 实体表 | 实体属性表 | 依赖基本信息表或类型信息表存在，是关于实体信息的属性补充信息，通常与依赖表的数据呈多对一关联。 |
| 业务作用表 | 外部数据表 | 市场信息表 | 储存结构化的市场数据信息，常用于查询展示及为关联业务提供市场数据进行加工，如股价、汇率信息等。 |
| 业务作用表 | 外部数据表 | 系统外请求表 | 常用于流程类系统中，用于第一时间记录外部原始数据，系统随后依据外部原始数据发起系统的业务流程。 |
| 业务作用表 | 交易表 | 交易主表 | 标示交易演进方向和演进过程的表，记录交易的一系列类型、状态等基本信息。 |
| 业务作用表 | 交易表 | 交易子表 | 在交易主流程中衍生的额外流程记录表，如系统内的任务流程、复杂业务处理流程或标准化业务处理模块、与外部系统交互流程信息的记录等。 |
| 业务作用表 | 交易表 | 附加信息表 | 在交易过程中产生的附加信息，本身无状态，依赖主表或子表存在。 |
| 业务作用表 | 日志表 |  | 用于跟踪用户或客户的操作日志，包括登录、数据修改、交易审批等操作。 |
| 技术作用表 | 操作表 |  | 用于记录各数据表的操作过程表，通常会记录每次数据变动的所有版本。 |
| 技术作用表 | 历史表 |  | 来自交易表的历史备份，与交易表不会重复，一般在系统上保留不超过 13 个月。 |
| 技术作用表 | 备份表 |  | 用于临时备份数据的表。 |
